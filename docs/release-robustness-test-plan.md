# Workbuddian 大版本发布 — 鲁棒性测试方案

> 日期：2026-08-09 · 出发点：**站在用户使用角度**
> 前置：v2.1.0 后新增 13 项功能,准备发布大版本
> 依据：历史手测报告 bug 模式（10 项）+ 新功能风险点分析（14 项）+ 用户操作流梳理

---

## 0. 测试总原则（用户视角）

1. **每个场景 = 真实用户会做的操作**（"发消息"、"切会话"、"重启 Obsidian"），不是内部实现验证。
2. **三明治策略**：jest 单测（逻辑层，已 644 项）→ e2e 自动化（关键链路）→ **手测压轴**（用户真实体验，不可自动化）。
3. **回归优先**：历史 bug 模式（第 1 节）必须有对应回归用例——这些是用户真实踩过的坑。
4. **鲁棒性兜底**：CLI 不可用、进程死亡、长会话、并发操作——用户日常会遇到。

## 3. 执行计划

### 阶段 1：自动化回归（先跑，30 分钟）
1. `npm test` → 644 全绿
2. `npm run build` → 无错误
3. `bash scripts/e2e/run-all.sh` → 基础链路 e2e(加载/面板/流式)
4. `node scripts/e2e/probe-ui.mjs` → 布局体检

### 阶段 2：手测压轴（重点，2-4 小时，用户视角）
1. **按测试矩阵逐项**：P0 全部 → P1 重要 → P2
2. **真机操作**：真实 Obsidian + 真实 CLI 登录(必须,否则批准/流式无法真测)
3. **双面板 + 重启恢复**：多次 Cmd+R,确认数据不丢
4. **每项记录**：✔ 通过 / ✗ 失败(现象 + 控制台 [WB] 日志)

### 阶段 3：问题修复 + 复测
1. 手测发现的 P0 问题 → 修复 → 复测该场景
2. 修复后重跑 `npm test` 确保无回归

## 4. 自动化 vs 手测（分工）

**自动化（jest + e2e）覆盖**：
- 纯逻辑（解析/排序/迁移/统计）→ jest 644 项
- 基础链路（加载/打开面板/发消息/流式回复）→ e2e run.mjs
- 布局体检 → probe-ui.mjs

**必须手测（自动化无法覆盖）**：
- 批准卡/权限（需真实 CLI 登录 + 人工判断批准）
- 流式视觉体验（逐字、思考块、diff 美感）
- 双面板真实交互（人同时操作两个面板）
- 进程死亡恢复（kill CLI 的时序）
- 无障碍（真实键盘 + 读屏）
- **所有新功能的真实用户体验**（模板/置顶/搜索/dual-pane 等手感）

> 手测是发布质量的最终裁决——自动化保底,手测定成败。
